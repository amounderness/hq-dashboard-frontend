# Proposed official HTML and ordinary-turnout import contract

**State:** Owner approved implementation for a new local, unpublished candidate on 5 October 2026. The [rc6 record](explorer-v2-barnsley-sheffield-rc6-2026-10-05.md) documents the result. This extends an import workflow, but does not change the SQLite schema or forecast method.

1. Let `import_reviewed_council_events.py` accept reviewed council HTML snapshots as well as declarations in PDF. Require an explicit media type, local snapshot file, SHA-256, official council URL and source note. Keep the original Sheffield PDF behavior. An HTML fixture may use `reported_votes_cast` when candidate votes reconcile but `ballots_issued` is not established. Store the council's stated turnout in `contest.turnout_rate`, with the ambiguity and rejected-paper count in the event and contest notes. Never silently calculate an issued-ballot figure from valid candidate votes.
2. Use the checked [Barnsley Penistone East fixture](../tools/explorer_v2/official_byelections_2026_barnsley_review.json) as the first HTML case. Verify its eight votes, one winner, canonical 2026 ward, source hash and absence of an existing 20 August contest. Keep Barnsley's May three-seat result, ordinary-source status and non-exhaustive event warning intact. Preserve the official result's “votes cast”/rejected-paper tension rather than changing the published 38.58% turnout.
3. Build a **separate** official-ordinary enrichment command for Sheffield's 7 May 2026 results. Pin the saved council HTML hash and require all 28 wards, 196 candidate vote/elected rows, electorates and seat counts to match the staged contests before writing. Add the council page as a source record and populate each contest's previously missing `turnout_rate` from the council's reported percentage. Retain the secondary source for candidate votes and document the four full-name variants; do not rename people or replace votes in this step. Record the four small one-seat turnout-arithmetic differences identified in the audit. For Beighton and Firth Park, label the reported turnout as council-supplied and do not derive a number of voters or ballots from the multiple candidate votes.
4. Work from a fresh copy of the rc5 store and package. Use one transaction per reviewed fixture, idempotent reruns, field-level checks, new manifest and package ID, and Leeds/Sheffield/Barnsley regression checks. Browser-check map turnout and ward history before any release decision. The current visual browser-control failure, council event-list completeness, historical boundaries, source licences and live owner/viewer controls remain separate gates.

The implementation approval covered only the **local, unpublished** rc6 candidate. Upload, merge, activation, production flags and live Leeds changes require separate review under `AGENTS.md`.
