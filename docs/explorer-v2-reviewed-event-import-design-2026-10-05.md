# Reviewed council-event import: owner design decision

**State:** Proposed importer contract for review. Source transcription and its read-only verifier exist; no 2026 result has been imported, packaged, uploaded or activated. This proposal changes the import workflow, not the SQLite schema or the forecast model.

## Immediate need

The rc4 Yorkshire package lacks two completed Sheffield City Council by-elections: Southey on 27 August 2026 and Walkley on 17 September 2026. The existing importer is intentionally locked to 2025, so changing its fixture or year checks would make the earlier rc4 work harder to reproduce. The [Sheffield source fixture](../tools/explorer_v2/official_byelections_2026_sheffield.json) is a checked transcription of the two [returning officer declarations](https://www.sheffield.gov.uk/your-city-council/elections/election-notices). Its verifier checks the original PDF SHA-256 values, canonical ward IDs, votes, winners, turnout and duplicates **without writing to the database**. Walkley's declaration gives Andrew Telford 541 votes; the council's aggregated index gives 258. The declaration figure is used because 2,315 + 56 + 112 + 541 + 59 + 1,249 + 8 rejected = 4,340 ballots issued.

## Proposed contract

1. Add a new `import_reviewed_council_events.py` command accepting a **fixture path** and a **new working-store directory**. Do not rewrite the 2025 importer or its fixture. Initially accept reviewed principal-council by-elections in England, with authority and event year taken from each record rather than hard-coded. Extend to other event types only with their own validators.
2. Require every event to identify its council, dated ward, poll date, seats, candidate votes and elected flags, electorate, ballots issued, rejected ballots, declared turnout, council declaration URL, downloaded PDF hash, and a source-review note. Preserve the printed party label in the fixture and write the app's canonical party label to `candidate_result`; the original label and PDF hash remain in the versioned transcription and event notes. No table change is needed for this first step.
3. Before any write, verify the source PDF hash, council/ward relationship, election type, candidate uniqueness, winner count, `sum(candidate votes) + rejected = ballots issued`, turnout within rounding tolerance, and absence of an existing council contest for the same ward/date. A source disagreement such as Walkley's 258/541 must have an explicit note and declaration precedence; do not silently copy the aggregated index.
4. Use one database transaction for all events in a fixture. Identify each imported event by council, date and ward; rerunning identical input is safe, while changed transcription bytes or partial prior records stop with an error. Preserve the existing ordinary 2026 Sheffield results. Update the Sheffield 2026 coverage reason to say council-sourced by-elections have been added, but keep `secondary_source_staged` and state that the event register is **not exhaustive**.
5. Work from a **copy** of the rc4 local store in a new dated staging directory. Build and validate a new package ID; never overwrite rc4 or its manifest. Verify ordinary and by-election records together, Leeds regressions, object hashes, and the resulting browser views before owner release review. No upload, approval, activation or production flag change follows merely from a successful build.

## Decision requested

Approve this no-schema-change import contract for implementation, including a new local rc5 candidate for the two Sheffield results. The source fixture is ready; approval of the contract does **not** approve publication or activation of rc5. The exact package hash, validation, browser checks and rollback path will be presented separately before any release action.
