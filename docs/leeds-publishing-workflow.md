# Leeds release workflow

The current pilot builds packages from audited local sources and stores immutable releases in private R2. The owner release screen can upload a completed package folder, validate it, approve its exact manifest hash, activate it and roll back an activation performed through that screen. It does not ingest raw election spreadsheets, resolve source disagreements, or replace the source audit and package-builder checks.

1. **Import into staging.** Keep original source files, URLs, retrieval dates, licences, and file hashes. Record which wards, dates and election types each source claims to cover. Do not put party-fed or individual voter data in a public-results release.
2. **Validate.** Check schema, ward and candidate identifiers, uniqueness, vote totals, turnout denominators, winner and seat consistency, geography joins, and comparison with already published records. Quarantine blank declarations and conflicts; never silently convert missing votes to zero.
3. **Review and approve.** Produce a human-readable difference report naming added, changed, missing and rejected records. The owner records a decision and reason for every exception and authorises an immutable package version. A later volunteer role should not gain this permission by default.
4. **Stage and test.** Build an immutable release. On Owner releases, select the complete package folder; the server verifies each object against the manifest and refuses changed bytes under an existing release ID. Retry the same folder after an interrupted upload. Validate all hashes, ward joins, election references, vote totals and manifest counts. Separately run the builder-specific checks and inspect the map, tables, snapshots, research context, reports and year transitions.
5. **Publish.** The owner records a reason, approves the exact manifest hash and activates it. The server repeats validation, checks that the live pointer has not changed, writes a start audit entry, and conditionally switches `active.json`. Verify signed-in use and signed-out denial before inviting viewers.
6. **Audit and rollback.** Owner actions are written as unique private R2 audit objects with identity, time, reason and old/new pointers. The screen can restore the previous validated release after an activation made by these controls. The older v0.3.0 rollback pointer predates this audit system and still needs the documented manual recovery route. Never overwrite package objects in place. Test independent backup restore separately.

The screen shows object-hash differences and release limits against the active package, not a field-by-field result diff. It is restricted by a server-verified Cloudflare Access identity; being a signed-in viewer alone does not grant owner actions. No party-fed or individual voter data belongs in these public-result packages. Further work should add source-file import, a record-level difference report and an independently tested backup restore before routine delegated releases.
